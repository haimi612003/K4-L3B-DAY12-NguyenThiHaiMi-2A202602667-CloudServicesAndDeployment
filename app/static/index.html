Kiến trúc khi chạy trên cloud

Một request đi qua những đâu, và mỗi thành phần chịu trách nhiệm gì.

Trình duyệt / curlgửi header X-API-Key, X-User-Id
→
Railway edgeHTTPS, domain *.up.railway.app, gán PORT=8080
→
Container agentimage multi-stage, user appuser, uvicorn nghe $PORT
⇄
Redisredis.railway.internal — lịch sử, rate limit, chi phí

Secret (AGENT_API_KEY) nằm trong Variables của Railway, không nằm trong repo hay image. Mọi state nằm ở Redis nên container có thể restart hoặc scale mà không mất dữ liệu.

Hành trình của một request theo thời gian

Đọc từ trên xuống. Mũi tên liền là request, mũi tên đứt là response; ô xám là xử lý bên trong một thành phần. Nếu một bước kiểm tra không đạt, app trả ngay mã lỗi ghi bên cạnh và dừng ở đó.

Code chính (rút gọn)

# app/rate_limiter.py — kiểm tra trước, ghi nhận sau
self.client.zremrangebyscore(key, 0, now - WINDOW_SECONDS)    # bỏ request ngoài cửa sổ
if self.client.zcard(key) >= self.limit:
    raise HTTPException(status_code=429, detail="rate limit exceeded")
self.client.zadd(key, {f"{now}:{uuid.uuid4().hex}": now})      # member duy nhất
self.client.expire(key, WINDOW_SECONDS)

# app/main.py — /ask
limiter.check(user_id)          # 429
guard.check(user_id)            # 402
history = store.get_history(user_id)
result = ask_llm(payload.question, history)

Vì sao đúng

  • == dừng ở ký tự khác đầu tiên → thời gian phản hồi lộ thông tin, đo đủ lần là dò được khóa.
  • Đếm theo phút đồng hồ có kẽ hở: 10 request lúc 10:00:59 + 10 request lúc 10:01:00 = 20 request trong 2 giây. Cửa sổ trượt 60 giây không có kẽ hở này.
  • Ghi trước rồi mới đếm sẽ chặn nhầm ngay ở request thứ 10.
  • Rate limit chặn tần suất, cost guard chặn tổng tiền — 10 request/phút nhưng mỗi request rất dài vẫn có thể đốt hết ngân sách.

Code chính

def install(self):
    for sig in (signal.SIGTERM, signal.SIGINT):
        self._previous[sig] = signal.getsignal(sig)   # nhớ handler của uvicorn
        signal.signal(sig, self.request_shutdown)     # rồi mới ghi đè

def request_shutdown(self, signum=None, frame=None):
    self.shutting_down = True                         # /health, /ready → 503
    previous = self._previous.get(signum)
    if callable(previous):
        previous(signum, frame)                       # trả lại cho uvicorn dừng server

Bằng chứng — thí nghiệm thật với Docker

0 → 2 → 4 → 6 → 8 → 10history_length khi scale 3 container sau nginx; mỗi container nhận 2 request
200 / 503tắt Redis ~35 s: /health 200, /ready 503, không container nào bị restart
tự hồi phụcbật Redis lại → cả 3 /ready về 200
exit 0SIGTERM → log service_stopped → thoát sạch

Vì sao đúng

  • Nhiều instance sau load balancer: câu 1 vào A, câu 2 vào B. Lịch sử trong RAM của A thì B không biết → agent "mất trí nhớ". Nếu dùng dict, history_length sẽ là 0, 0, 0, 2, 2, 2 thay vì tăng đều.
  • Mỗi tín hiệu chỉ có một handler: ghi đè mà không gọi lại handler của uvicorn thì server không bao giờ tự dừng và bị SIGKILL.
